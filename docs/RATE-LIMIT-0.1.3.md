# NVIDIA MCP 限流与 0.1.3 处理

## 已确认的服务端行为

本机 NVIDIA App 返回过以下拒绝响应：

```json
{"code":-32029,"data":{"retryAfter":2},"message":"Rate limited: too many tool calls. Try again in 2s."}
```

`-32029` 表示此次工具调用被限流，`retryAfter` 表示等待秒数。本机日志中有 1、2、7、9 秒的返回值；2 秒只是本次等待时间，不能据此推断“每两秒允许一次”。

查到的 [NVIDIA 官方连接说明](https://github.com/NVIDIA/nvidia-app-skills/blob/main/skills/nvidia-app/references/connection.md) 和 [工具契约](https://github.com/NVIDIA/nvidia-app-skills/blob/main/skills/nvidia-app/references/mcp-tool-contract.md) 没有列出具体限流配额。每秒或每分钟允许多少次、计数是否按客户端共享、采用固定窗口还是令牌桶，目前均未核实。不能拿其他 MCP 服务的限额替代 NVIDIA 的限额。

旧版一次恢复流程会连续读取多次状态，验证期间还会每两秒读取；读取状态也属于工具调用。这种调用节奏会增加触发限流的可能性。

## 本版客户端处理

- 同一进程的 MCP 连接、可用性测试共用请求节流器，工具调用初始至少间隔五秒。这个数字是本程序的保守策略，不是 NVIDIA 公布的限额。
- 收到限流后遵守服务端等待时间，并增加 250 毫秒余量；再次限流时继续延长本地工具调用间隔，最高六十秒。服务端要求更长的等待时，以其等待时间为准。
- HTTP 与 stdio 之间共享本进程的冷却，不通过切换传输方式重试限流请求；协议探测也不在限流后立即改用旧协议补发。
- 普通状态读取被限流时显示未知和等待提示，不累计为接口可用性失败，不因限流降级到注册表或快捷键。
- MCP 模式恢复时复用当次刚读取的明确关闭状态，去掉同一轮的两次重复读取；开启仍明确传递 `enable: true`。
- 发送开启后，根据请求节流和服务端冷却延长确认时间。等待期间不重复发送开启；只有独立读取到开启状态才可能通知。
- 明确遭到限流拒绝的开启请求，不会被算作已成功发起的恢复操作，因此后续正常检测到开启也不会误发成功通知。
- 测试按钮复用连接；等待不忙循环，可以被暂停、设置修改或退出打断。

检测间隔设置是基础间隔。限流后，MCP 的实际请求间隔可能更长；注册表的基础轮询间隔不受本地 MCP 工具调用间隔控制。其他进程或客户端是否共享 NVIDIA 侧额度尚未确认，本程序也不能控制它们的请求。

## 验证与交付

- 36 项测试通过，严格 Clippy 检查通过，发布编译完成。
- 测试覆盖服务端等待时间解析、无效提示的保守等待、冷却不可被更短提示覆盖、请求间隔、重复限流减速、取消请求，以及延后确认和拒绝请求不误发成功通知。
- 网络解析测试使用本机模拟服务；没有向 NVIDIA 进行限流压力测试，没有为测试主动切换即时回放。
- 当前现场程序没有被自动替换。使用前从旧版设置中点击退出，再运行 0.1.3；配置继续沿用。自启路径若改变，需要在新版中关闭再开启自启更新路径。
- 本版没有重新进行十分钟内存和 CPU 采样。
